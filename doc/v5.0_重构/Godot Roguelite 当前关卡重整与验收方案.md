# Godot Roguelite 项目重整与当前关卡高标准验收方案

**文档状态：** 执行版
**适用阶段：** 当前关卡重整、核心玩法验证、角色与场景美术重建
**项目方向：** C++ Godot Roguelite
**视觉参考方向：** Hyper Light Drifter 式的画面结构、色彩节奏、空间阅读和战斗表现
**核心原则：** 不降低质量标准，不以临时方案替代正式实现，不在基础表现未稳定前继续扩展内容。

---

## 一、项目现状与本阶段结论

当前项目已经完成了相当数量的功能、场景、系统和流程开发。现阶段的问题并不是项目缺少代码或缺少内容，而是已有内容没有形成统一、可信、自然的整体表现。

主要问题集中在以下方面：

1. 玩家角色的移动帧、重心、朝向和动作衔接不自然。
2. 射击动作与移动状态之间缺乏统一的动作逻辑。
3. 敌人的移动、转向、受击和战斗反馈不够清晰。
4. 相机没有完全服务于移动、瞄准、射击和场景阅读。
5. 关卡空间、角色比例、场景装饰和视觉焦点之间缺乏统一标准。
6. 当前美术资产的尺寸、透视、锚点、色彩、像素密度和风格不一致。
7. UI、场景、人物、敌人和特效尚未形成统一的视觉语言。
8. 已有系统数量较多，但当前关卡还没有达到可作为项目质量基准的程度。

因此，本阶段不重新创建空项目，也不继续在旧场景中无边界地增加补丁。

项目采用以下方式重整：

> 保留现有仓库和已经完成的系统基础，在当前项目内重新建立一条干净、可控、可验收的关卡主线。

本阶段的工作对象不是单个房间，也不是整条房间链，而是一个完整的当前关卡。

当前关卡必须成为后续所有关卡、角色、敌人、动画、相机和美术制作的质量基准。

### 4.1 第一关重构优先级

当前重构不是继续堆叠内容，而是把第一关重新做成一个可作为正式基准的样板关。

第一关优先级必须按下面顺序推进：

1. 相机和视角。
2. 关卡空间和构图。
3. 玩家移动、射击、武器切换和状态表现。
4. 敌人移动、受击和死亡表现。
5. UI 可读性和信息层级。
6. 截图对比和最终验收。

其中，相机、视角和场景空间是第一关的首要工作，不允许被后续关卡链、剧情包装或额外系统挤到后面。

第一关的目标不是“能跑”，而是“像正式作品一样可读、可控、可验证”。

## 二、本阶段不可违反的原则

### 2.1 不采用退化方案

本阶段禁止使用以下方式掩盖问题：

* 不使用静态单帧长期替代正式移动动画。
* 不通过隐藏角色腿部、增加过量阴影或特效掩盖脚底漂移。
* 不通过降低动画帧数掩盖动作不连贯。
* 不通过关闭角色转向掩盖方向系统问题。
* 不通过放大角色或缩小场景掩盖比例问题。
* 不通过镜头强制锁定掩盖关卡构图问题。
* 不通过增加屏幕震动掩盖射击反馈不足。
* 不通过增加大量粒子掩盖受击动作不清晰。
* 不通过延长无敌时间掩盖敌人受击逻辑或碰撞逻辑问题。
* 不使用临时占位美术进入最终验收。
* 不以“之后再统一”为理由继续引入风格不一致的资产。

任何无法达到验收标准的内容，都应返回设计、资产或实现阶段重新处理，而不是降低验收标准。

### 2.2 当前关卡优先

在当前关卡达到正式验收标准前：

* 不扩展新关卡。
* 不扩展新的房间链。
* 不增加新 Boss。
* 不增加新的大型剧情系统。
* 不增加新的主题区域。
* 不增加新的复杂技能树。
* 不增加与当前闭环无关的系统。
* 不继续批量生产未经验证的角色或场景美术。

已有代码、场景和系统可以保留，但冻结项不进入当前开发主线，也不作为本阶段必须修改的对象。

### 2.3 所有新增内容必须服务于统一标准

每个新资产、新动作、新场景和新 UI 元素，在进入项目之前必须回答以下问题：

1. 它是否符合统一的视觉风格？
2. 它是否符合统一的比例和透视？
3. 它是否能在实际游戏缩放比例下清晰阅读？
4. 它是否具有正确的锚点和空间位置？
5. 它是否增强核心玩法，而不是增加视觉噪声？
6. 它是否能够通过明确的验收测试？
7. 它是否会增加新的风格分支或技术债务？

无法明确回答以上问题的内容，不进入正式资源库。

## 3.2 冻结内容

冻结不等于删除，也不要求立即重构。

冻结内容保持当前代码和资源状态，不再进入当前开发主线。

包括但不限于：

* 当前关卡之外的新关卡。
* 未进入当前关卡验收范围的房间。
* Boss 扩展。
* 第二套大型角色能力系统。
* 多主题区域。
* 大规模叙事扩展。
* 卡牌系统扩展。
* 复杂技能树。
* 大规模装备系统。
* 非必要的 Shader 扩展。
* 不影响当前关卡闭环的 UI 页面。
* 不影响当前关卡闭环的过场动画。
* 未经过视觉规范验证的旧美术组合。

冻结内容不得影响当前关卡的构建、启动、性能和测试。

## 四、当前关卡定义

当前关卡不是测试房间，也不是功能展示场景。

它必须是一段可以独立运行、完整体验和正式验收的游戏内容。

玩家进入当前关卡后，应能够完成以下体验闭环：

1. 进入关卡。
2. 识别玩家位置、主要路径和当前威胁。
3. 自然移动。
4. 调整方向和瞄准。
5. 使用当前武器攻击敌人。
6. 在移动和射击之间自然切换。
7. 切换武器。
8. 识别不同武器的表现和用途差异。
9. 躲避或处理敌人的进攻。
10. 对敌人造成连续伤害。
11. 清除敌人。
12. 得到明确的战斗完成反馈。
13. 进入关卡结算或下一阶段入口。
14. 玩家死亡后能够正常重开并恢复完整状态。

当前关卡应当体现项目最终方向，而不是仅仅证明代码能够运行。

## 五、核心玩法重新定义

本项目当前阶段的核心玩法定义为：

> 玩家通过精准、自然且具有节奏感的移动、瞄准、射击和武器切换，在清晰可读的空间中应对敌人，并通过位置选择、攻击时机和武器选择完成战斗。

核心玩法不是“拥有多少系统”，而是以下行为是否能够形成持续、清晰、有反馈的决策循环：

> 观察 → 移动 → 判断距离 → 选择武器 → 瞄准 → 攻击 → 躲避 → 调整位置 → 再次攻击。

### 5.1 核心玩法必须具备的品质

#### 移动具有控制感

玩家应能够准确预期角色下一时刻的位置。

移动不能出现：

* 明显滑步。
* 输入停止后继续漂移。
* 方向改变时重心瞬移。
* 动画速度与实际位移不一致。
* 角色移动方向与身体朝向完全失去关联。
* 对角线移动速度异常。
* 贴墙时抖动。
* 小范围调整时难以控制。

#### 瞄准具有明确方向

玩家必须能够快速识别：

* 当前瞄准方向。
* 当前武器朝向。
* 子弹发射方向。
* 攻击起点。
* 攻击有效范围。
* 当前攻击是否命中。

瞄准系统不得让角色视觉朝向、武器朝向和弹道方向产生冲突。

#### 射击具有完整动作逻辑

一次射击至少包含：

1. 射击准备。
2. 武器发力。
3. 子弹或攻击效果产生。
4. 后坐或动作反馈。
5. 动作恢复。

射击动作不应只是生成一个投射物。

动画、音效、枪口效果、后坐反馈和命中反馈应发生在一致的时间点。

#### 武器切换具有明确价值

武器切换不能只是图标和数值变化。

不同武器至少应在以下两个以上维度存在明确区别：

* 射程。
* 射速。
* 单次伤害。
* 弹道。
* 攻击范围。
* 移动限制。
* 后坐。
* 命中反馈。
* 对敌策略。
* 资源消耗。
* 攻击节奏。

玩家必须能够通过画面和操作感立即确认武器已经切换完成。

#### 敌人形成可读压力

敌人不能只是持续朝玩家移动的碰撞体。

敌人必须至少具有：

* 清晰的移动状态。
* 清晰的目标方向。
* 清晰的攻击准备。
* 清晰的攻击发生时点。
* 清晰的受击反馈。
* 清晰的死亡反馈。
* 可理解的威胁范围。
* 可被玩家学习和应对的行为规律。

### 5.2 当前阶段暂不接受的核心玩法状态

以下状态均不能通过验收：

* 玩家只能依赖持续后退完成战斗。
* 敌人只会直线追击。
* 射击没有明显时机和节奏。
* 武器切换没有战术意义。
* 玩家无法通过移动技术降低风险。
* 玩家攻击与敌人反馈之间缺少明确因果关系。
* 战斗结果主要依赖数值碾压。
* 场景空间对战斗没有影响。
* 玩家无法判断敌人何时攻击。
* 高频攻击导致敌人受击反馈完全不可读。

## 六、玩家角色表现标准

## 6.1 角色视觉规范

玩家角色必须建立独立的角色视觉规范文档，至少包含：

* 角色正面结构。
* 角色背面结构。
* 角色侧面结构。
* 主要颜色。
* 辅助颜色。
* 高亮颜色。
* 轮廓颜色。
* 身体比例。
* 头身比例。
* 武器尺寸。
* 武器持握位置。
* 脚底位置。
* 角色中心点。
* 阴影中心。
* 朝向规则。
* 动作夸张程度。
* 实际游戏显示尺寸。
* 各动画统一画布尺寸。
* 各动画统一脚底锚点。
* 各动画统一角色缩放比例。

所有玩家帧必须属于同一个角色设计版本。

禁止将不同生成批次、不同服装结构、不同武器形态、不同身体比例的图片直接组合为同一套动画。

## 6.2 玩家移动动画

玩家移动动画必须覆盖：

* 静止。
* 起步。
  -持续移动。
* 转向。
* 停步。
* 必要的方向变化。

每一帧必须满足：

* 脚底锚点稳定。
* 角色中心不无故漂移。
* 身体体积保持稳定。
* 武器长度保持稳定。
* 盾牌或装备位置连续。
* 头部大小稳定。
* 服装轮廓连续。
* 光源方向一致。
* 阴影方向一致。
* 帧间不存在角色版本变化。

动画速度必须与实际位移速度匹配。

角色每个完整步态周期所对应的游戏位移，应经过实际测量和调整，避免角色脚步移动距离与场景位移不一致。

## 6.3 玩家转向

玩家转向必须由明确的角色控制设计决定，不能同时混用多套规则。

需要统一以下关系：

* 移动方向。
* 瞄准方向。
* 身体朝向。
* 武器朝向。
* 头部朝向。
* 动画方向。

最终表现必须让玩家能够立即理解角色当前在向哪里移动、向哪里瞄准、向哪里攻击。

不允许直接旋转整张具有固定透视和固定光照的角色插画来模拟全部方向。

## 6.4 玩家射击动作

射击动作必须与当前武器对应。

每种武器至少需要定义：

* 射击准备帧。
* 开火帧。
* 恢复帧。
* 枪口位置。
* 弹道起点。
* 后坐方向。
* 武器摆动。
* 射击音效时点。
* 枪口效果时点。
* 投射物生成时点。
* 屏幕或相机反馈强度。

移动射击时，不允许直接用上半身射击动画覆盖整个人物移动动画而产生脚部冻结或滑步。

应建立清晰的动画分层或完整组合动画方案。

## 6.5 武器切换

武器切换必须包含：

* 输入响应。
* 当前攻击终止或收尾规则。
* 切换开始。
* 旧武器退出。
* 新武器进入。
* UI 更新。
* 角色外观更新。
* 攻击参数更新。
* 音效反馈。
* 可再次攻击的明确时点。

切换过程中不得出现：

* 旧武器图像残留。
* 新旧攻击参数混用。
* 投射物类型错误。
* 射击音效错误。
* UI 已切换但角色未切换。
* 角色已切换但攻击数据未切换。
* 连续快速切换导致状态卡死。
* 死亡或暂停后武器状态异常。

## 七、敌人表现标准

## 7.1 敌人视觉规范

每一种敌人必须建立独立规范，包括：

* 身体比例。
* 实际显示尺寸。
* 碰撞体范围。
* 脚底锚点。
* 阴影尺寸。
* 移动方向。
* 攻击方向。
* 受击方向。
* 主要色板。
* 威胁识别色。
* 攻击预警色。
* 死亡表现。

敌人的外观必须在实际游戏显示尺寸下清晰可辨。

不能依赖放大查看才能理解敌人的动作。

## 7.2 敌人移动

敌人移动必须具备：

* 明确的起步。
* 稳定的移动循环。
* 合理的转向。
* 停止或攻击前的状态变化。
* 与实际速度匹配的步态。
* 与地面接触稳定的脚底。
* 不漂浮的阴影关系。

敌人不得出现：

* 连续左右抖动。
* 贴墙振荡。
* 路径点附近反复转向。
* 身体朝向与移动方向无关。
* 移动动画速度与实际位移不一致。
* 攻击时仍保持完整移动速度。
* 死亡后继续移动。
* 受到连续攻击时位置异常跳动。

## 7.3 敌人受击

当前关卡中的敌人受到伤害时不设置伤害无敌帧。

每次合法命中都必须进行独立伤害结算。

同时必须保证：

* 单颗投射物不能在同一逻辑命中中重复结算。
* 持续碰撞攻击必须有明确的伤害频率定义。
* 多颗投射物同时命中可以分别结算。
* 每次伤害都具有可读反馈。
* 高频攻击不会造成画面完全闪白。
* 受击反馈不会阻断敌人必要的状态逻辑。
* 受击反馈不会导致敌人长期无法行动，除非这是明确设计的硬直机制。

敌人受击反馈可由以下内容组合：

* 短时颜色变化。
* 局部闪光。
* 受击方向位移。
* 小幅硬直。
* 受击音效。
* 命中特效。
* 伤害数字。
* 生命值变化。
* 特定部位反馈。

反馈强度必须与伤害强度相匹配。

## 7.4 敌人攻击

敌人攻击必须具备明确的阶段：

1. 发现或锁定玩家。
2. 接近或调整位置。
3. 攻击预备。
4. 攻击发生。
5. 攻击恢复。
6. 再次进入移动或攻击决策。

玩家必须能够通过动画、音效或特效识别攻击发生前的危险信号。

禁止敌人在没有视觉预警的情况下突然造成近距离伤害。

---

## 八、相机系统重新定义

相机不是独立的视觉组件，而是核心操控和关卡阅读系统的一部分。

相机必须同时服务于：

* 玩家移动。
* 玩家瞄准。
* 玩家射击。
* 敌人观察。
* 危险识别。
* 场景方向阅读。
* 入口和出口识别。
* 战斗空间判断。
* UI 信息阅读。

## 8.1 相机目标

相机应当让玩家始终能够看到：

* 玩家自身。
* 当前主要攻击方向。
* 即将进入的空间。
* 主要敌人威胁。
* 必要的躲避空间。
* 场景中的关键障碍。
* 当前关卡的视觉焦点。

## 8.2 相机跟随

相机跟随需要定义：

* 基础跟随速度。
* 加速阶段。
* 停止阶段。
* 玩家快速转向时的响应。
* 瞄准方向偏移。
* 鼠标位置或右摇杆影响。
* 房间边界限制。
* 战斗状态影响。
* 受击反馈。
* 射击反馈。
* Boss 或关键事件影响。

相机不得出现：

* 玩家轻微移动导致镜头持续晃动。
* 镜头明显落后于玩家。
* 玩家停止后镜头缓慢漂移。
* 靠近边界时突然跳动。
* 相机限制范围与真实关卡范围不一致。
* 瞄准偏移导致玩家被挤到屏幕边缘。
* 射击震动破坏瞄准精度。
* 镜头运动导致像素美术出现不必要的亚像素抖动。

## 8.3 相机与关卡边界

当前关卡必须拥有唯一、明确的可玩区域定义。

以下内容必须使用统一的数据来源或保持严格一致：

* 物理边界。
* 可行走区域。
* 相机限制。
* 背景覆盖范围。
* 导航区域。
* 敌人活动范围。
* 出生区域。
* 出口区域。
* 战斗触发区域。
* 装饰安全区域。

禁止在不同脚本和场景节点中分别写入互相不一致的边界数值。

### 8.4 第一关的相机要求

第一关相机不是默认跟随器，而是当前关卡阅读系统的一部分。

第一关相机必须满足：

* 能稳定服务玩家移动。
* 能稳定服务瞄准和射击。
* 能让玩家持续读到前方空间。
* 能让敌人威胁保持清晰。
* 能让关卡出口和关键区域保持可识别。
* 能与真实关卡边界一致。
* 能避免边界处出现明显跳变。
* 能避免镜头本身成为视觉噪声。

如果相机无法满足以上要求，第一关不得进入视觉验收。

## 九、当前关卡场景标准

## 9.1 空间结构

当前关卡必须具备清晰的空间层级：

* 玩家进入区域。
* 初始观察区域。
* 主要战斗区域。
* 次要移动区域。
* 视觉焦点区域。
* 危险区域。
* 出口或结算区域。

场景不能只是均匀铺满装饰。

必须通过以下方式引导玩家：

* 地形形状。
* 明暗变化。
* 色彩变化。
* 道路走向。
* 装饰密度。
* 光源。
* 建筑或遗迹方向。
* 敌人分布。
* 出入口结构。

## 9.2 视觉焦点

一个画面中必须存在明确的主要视觉焦点。

焦点可以是：

* 玩家。
* 敌人。
* 出口。
* 交互对象。
* 关键建筑。
* 光源。
* 战斗目标。

背景装饰不得与玩家、敌人、子弹、攻击预警或出口争夺视觉注意力。

## 9.3 地面与角色关系

角色必须明确站在地面上。

需要统一：

* 角色脚底位置。
* 地面透视。
* 阴影方向。
* 阴影软硬。
* 阴影透明度。
* 遮挡关系。
* 墙体高度。
* 可行走区域和不可行走区域的视觉区分。

不得通过任意添加椭圆阴影解决所有角色的落地问题。

阴影必须符合场景光源和角色高度。

## 9.4 场景过渡

当前关卡内部的区域过渡必须自然。

过渡应通过以下内容完成：

* 地面材质渐变。
* 装饰密度变化。
* 色温变化。
* 光照变化。
* 空间宽度变化。
* 建筑结构变化。
* 音效变化。
* 敌人配置变化。

禁止两个完全不同风格的区域直接硬拼。

区域之间必须存在共享元素，使玩家能够理解它们属于同一关卡。

## 9.5 第一关场景重构要求

第一关必须先做成单关卡样板，而不是房间链节点。

第一关场景重构必须至少回答以下问题：

* 玩家从哪里进入。
* 玩家第一眼看到什么。
* 主路径在哪里。
* 战斗发生在哪里。
* 敌人从哪里形成压力。
* 玩家往哪里撤退或绕行。
* 出口在哪里。
* 场景的视觉焦点是什么。
* 光线和暗部如何帮助读图。

第一关场景不能只是“背景 + 边界 + 敌人刷点”。它必须具备完整的空间叙事和战斗导向。

第一关场景验收时，必须检查：

* 角色比例是否可信。
* 角色是否能自然站在地面上。
* 前景、中景、背景是否有层次。
* 主路径是否一眼可辨。
* 出口是否能在不解释的情况下被找到。
* 场景是否存在资源拼贴感。
* 场景是否存在与玩法无关的视觉噪声。

## 十、美术资产制作规则

## 10.1 资产类型判断

制作每一个视觉元素前，必须先确定它属于以下哪一种资产：

### Figma 矢量

适用于：

* UI 布局。
* 面板。
* 按钮。
* 进度条。
* 简单几何框体。
* 文本排版。
* 对齐和间距设计。
* 页面原型。
* 状态组件。
* 简单装饰线条。

### SVG 矢量

适用于：

* 简单图标。
* 单色符号。
* 可缩放状态标记。
* 几何形状。
* 简单箭头。
* 简单徽章。
* 不依赖复杂纹理的 UI 图形。

### AI 重新生成位图

适用于：

* 玩家角色。
* 敌人角色。
* 复杂角色动画基础帧。
* 复杂场景背景。
* 建筑。
* 遗迹。
* 实体道具。
* 武器插画。
* 卡牌插画。
* 复杂图标。
* 装饰坠子。
* 植物。
* 岩石。
* 光效基础素材。
* 具有材质、光照和体积的资产。

不得为了减少工作量，将明显需要位图表现的复杂对象强行改成低质量矢量。

也不得将简单 UI 几何元素全部交给 AI 生图，造成尺寸、边缘和对齐不可控。

## 10.2 原图使用限制

禁止：

* 直接裁切原图中的元素作为最终资产。
* 直接抠取原图中的角色、图标或装饰。
* 描摹原图中的具体形状。
* 对参考游戏画面进行像素级复刻。
* 复制具体角色设计。
* 复制具体地图结构。
* 复制具体 UI 布局细节。

参考内容仅用于分析：

* 画面层级。
* 色彩节奏。
* 空间构图。
* 动作节奏。
* 光照关系。
* 战斗信息表达。
* 视觉引导方式。

最终资产必须形成项目自己的角色、世界、图标和视觉语言。

## 10.3 GPT Image 生成规则

使用 GPT Image 进行基础美术生成时，必须先提供完整资产规范。

每次生成任务至少应包含：

* 资产用途。
* 实际游戏尺寸。
* 画布比例。
* 观察角度。
* 角色朝向。
* 光源方向。
* 色板范围。
* 背景要求。
* 透明背景要求。
* 轮廓要求。
* 材质要求。
* 动作状态。
* 脚底锚点要求。
* 武器位置要求。
* 禁止出现的内容。
* 与现有资产的一致性要求。

禁止只使用“生成一个类似 Hyper Light Drifter 的人物”作为提示词。

角色生成应强调项目自己的视觉设定，并只借鉴高层次的构图、色彩和节奏特征。

## 10.4 网格资产图规则

复杂资产应优先批量生成在统一网格资产图中。

适合网格生成的内容包括：

* 同类植物。
* 同类岩石。
* 同类场景装饰。
* 武器图标。
* 状态图标。
* 掉落物。
* 小型敌人设计变体。
* UI 实体图标。
* 装饰坠子。
* 同一角色的动作关键帧草案。

网格资产图必须满足：

* 每个单元格尺寸一致。
* 资产之间有足够间距。
* 背景统一。
* 光源统一。
* 视角统一。
* 比例统一。
* 不互相重叠。
* 不出现跨格阴影。
* 每个资产完整显示。
* 不裁切武器、头部、脚部或装饰。

切分后需要：

1. 检查透明背景。
2. 清理边缘杂色。
3. 裁除透明边界。
4. 保留统一安全边距。
5. 设置正确锚点。
6. 检查实际游戏尺寸。
7. 检查缩放后的清晰度。
8. 登记资产来源和生成批次。

## 10.5 动画资产规则

AI 生成的角色图不能直接被视为可用动画帧。

动画帧进入项目之前必须经过：

* 角色一致性检查。
* 服装一致性检查。
* 武器一致性检查。
* 身体比例检查。
* 脚底锚点校正。
* 轮廓连续性检查。
* 帧间位移检查。
* 光照一致性检查。
* 色彩一致性检查。
* 实际播放测试。
* 实际移动速度匹配测试。

如关键帧无法自然插入完整动作，应重新生成或重新绘制，不得依靠代码插值强行补救。

## 十一、UI 制作规则

## 11.1 UI 信息优先级

UI 的第一目标是快速、准确地传递信息。

信息优先级应按照以下顺序组织：

1. 当前生命状态。
2. 当前武器。
3. 当前可执行操作。
4. 当前资源或弹药。
5. 当前战斗目标。
6. 当前异常状态。
7. 次要装饰信息。

UI 装饰不得降低文字、数值、图标和状态的可读性。

## 11.2 文本规则

同一句话中的普通文字和高亮数值必须使用同一个 TextNode 或同一个支持局部样式的富文本节点。

例如：

“暴击率提升 25%”

不得拆分为：

* “暴击率提升”
* “25%”

两个独立文字节点。

需要通过局部颜色、字体粗细、描边或字号完成强调。

这样可以避免：

* 基线不一致。
* 间距错误。
* 多语言错位。
* 分辨率变化后分离。
* 动态数值更新时布局破坏。

## 11.3 UI 布局规则

所有 UI 必须建立：

* 统一栅格。
* 统一安全边距。
* 统一组件间距。
* 统一圆角。
* 统一描边。
* 统一阴影。
* 统一字体层级。
* 统一图标尺寸。
* 统一状态颜色。
* 统一交互反馈。

禁止凭视觉感觉逐个手动放置，而没有可复用的布局规则。

## 11.4 UI 图标规则

UI 图标必须在实际显示尺寸下测试。

每个图标必须满足：

* 轮廓清晰。
* 含义明确。
* 颜色数量可控。
* 与背景有足够对比。
* 相同级别图标体积一致。
* 图标中心稳定。
* 不依赖小细节表达含义。
* 禁用状态和可用状态能够区分。

复杂实体图标使用 AI 位图重新生成。

简单功能图标使用 SVG。

## 十二、截图对比与视觉验收流程

每个场景、UI 页面和关键角色状态完成后，必须进行截图对比。

截图应至少覆盖：

* 默认游戏分辨率。
* 玩家静止。
* 玩家移动。
* 玩家转向。
* 玩家射击。
* 玩家切换武器。
* 多名敌人出现。
* 敌人受击。
* 敌人死亡。
* 玩家受伤。
* 关卡完成。
* 关键 UI 状态。
* 屏幕边缘位置。
* 最复杂战斗画面。

每次截图检查以下内容：

### 布局

* 主要元素是否处于正确位置。
* 玩家是否处于合理视觉区域。
* UI 是否遮挡游戏信息。
* 场景焦点是否明确。
* 出口是否能够识别。

### 重叠

* 角色是否被不合理遮挡。
* UI 是否互相覆盖。
* 特效是否遮挡敌人攻击。
* 伤害数字是否堆叠。
* 阴影是否穿过墙体。
* 武器是否穿过角色身体。

### 居中

* 图标是否视觉居中。
* 按钮文字是否视觉居中。
* 角色是否在统一画布中稳定对齐。
* 状态标记是否位于目标中心。

### 比例

* 玩家与敌人的比例是否统一。
* 武器与角色身体是否协调。
* 场景装饰是否过大或过小。
* UI 图标是否属于同一尺寸体系。
* 特效是否与攻击强度匹配。

### 颜色

* 玩家是否能从背景中识别。
* 敌人是否能从背景中识别。
* 攻击预警是否足够明确。
* 受击反馈是否过曝。
* UI 状态色是否一致。
* 场景是否存在无意义的颜色竞争。

### 缺失细节

* 是否缺少阴影。
* 是否缺少枪口反馈。
* 是否缺少受击反馈。
* 是否缺少武器切换反馈。
* 是否缺少出口提示。
* 是否缺少危险提示。
* 是否缺少状态变化。
* 是否存在乱码或占位文字。
* 是否存在未替换的临时资产。

检查后必须迭代修正，并重新截图。

不得以单次截图结果作为最终结论。

## 十三、技术实现要求

## 13.1 状态统一

玩家和敌人的表现必须由明确的状态机驱动。

玩家状态至少包括：

* Idle。
* Move。
* Aim。
* Fire。
* WeaponSwitch。
* Hit。
* Dead。

敌人状态至少包括：

* Idle。
* Alert。
* Chase。
* AttackPrepare。
* Attack。
* Recover。
* Hit。
* Dead。

动画、音效、移动、碰撞和攻击逻辑必须与状态保持一致。

不得由多个脚本分别修改同一表现状态而没有统一控制。

## 13.2 动画事件

以下事件应由动画时间点或统一动作时间轴控制：

* 枪口效果出现。
* 投射物生成。
* 攻击判定启用。
* 攻击判定关闭。
* 脚步音效。
* 武器切换完成。
* 受击反馈开始。
* 死亡碰撞关闭。
* 死亡动画完成。

避免使用多个互不关联的 Timer 猜测动画时点。

## 13.3 像素和采样

如果最终采用像素化角色或像素风资产，必须统一：

* 基准像素密度。
* 导入过滤方式。
* 纹理压缩方式。
* 缩放倍数。
* 相机缩放。
* 像素对齐。
* 旋转策略。
* Shader 采样方式。

不得同时存在锐利像素角色、模糊背景、平滑矢量图标和高分辨率插画，却没有统一的组合规则。

## 13.4 调试工具

当前关卡必须提供可开关的调试显示：

* 玩家碰撞体。
* 敌人碰撞体。
* 攻击判定范围。
* 投射物碰撞体。
* 相机限制。
* 可玩区域。
* 导航区域。
* 敌人目标位置。
* 玩家脚底锚点。
* 精灵中心点。
* 枪口位置。
* 当前状态名称。
* 当前武器名称。
* 当前动画名称。
* 当前动画帧。
* 当前移动速度。

调试显示仅用于开发，不进入正式画面。

## 十四、高标准验收标准

当前关卡只有在全部达到以下标准后，才允许进入下一阶段。

## 14.1 玩家移动验收

* 玩家起步动作自然。
* 玩家持续移动动作自然。
* 玩家停止动作自然。
* 玩家转向动作自然。
* 玩家每一帧脚底稳定。
* 玩家身体中心无异常漂移。
* 动画速度与实际移动速度一致。
* 八方向或项目规定方向均无明显视觉错误。
* 对角线移动速度正确。
* 贴墙移动不抖动。
* 快速连续改变方向不出现状态卡顿。
* 移动时角色轮廓和装备保持一致。
* 连续观察一分钟无明显循环跳帧。

任何一项不通过，玩家移动不得验收。

## 14.2 玩家射击验收

* 射击方向准确。
* 武器朝向准确。
* 枪口位置准确。
* 投射物起点准确。
* 动画开火帧与投射物生成时点一致。
* 音效与开火时点一致。
* 枪口效果与开火时点一致。
* 后坐反馈自然。
* 射击后恢复自然。
* 移动射击不滑步。
* 连续射击动画不跳变。
* 射击过程中快速转向不产生错误弹道。
* 不同武器的射击节奏明确不同。
* 射击反馈不会破坏瞄准精度。

任何一项不通过，射击系统不得验收。

## 14.3 武器切换验收

* 武器切换输入响应稳定。
* 角色外观正确切换。
* UI 正确切换。
* 武器参数正确切换。
* 射击音效正确切换。
* 投射物类型正确切换。
* 切换动作完整。
* 可攻击时点明确。
* 快速连续切换不出现状态错误。
* 切换时移动状态正常。
* 切换时受到伤害不会卡死。
* 死亡重开后武器状态正确。
* 暂停恢复后武器状态正确。
* 每种武器具有可感知的战术差异。

任何一项不通过，武器系统不得验收。

## 14.4 敌人移动验收

* 敌人起步自然。
* 敌人移动循环自然。
* 敌人脚底稳定。
* 敌人朝向正确。
* 敌人移动速度与动画一致。
* 敌人路径选择合理。
* 敌人贴墙不抖动。
* 多名敌人不会完全重叠。
* 敌人进入攻击状态时动作明确。
* 敌人攻击后恢复自然。
* 敌人死亡后停止全部移动逻辑。
* 敌人不会因为连续受击产生异常位移。
* 连续观察一分钟无明显动画错误。

任何一项不通过，敌人移动不得验收。

## 14.5 敌人受击验收

* 每次合法命中都正确扣除生命值。
* 敌人没有伤害无敌帧。
* 单颗投射物不会异常重复伤害。
* 多颗投射物可以分别结算。
* 受击反馈方向正确。
* 受击反馈强度与伤害匹配。
* 高频攻击下仍能清晰判断命中。
* 高频攻击不会导致敌人长时间纯白或不可见。
* 受击不会破坏敌人必要状态。
* 死亡发生时停止后续伤害结算。
* 死亡反馈清晰。
* 连续攻击过程中没有漏伤害或异常多段伤害。

任何一项不通过，伤害系统不得验收。

## 14.6 相机验收

* 相机跟随平稳。
* 玩家小幅移动不会引起明显抖动。
* 玩家快速移动时相机不会严重滞后。
* 玩家停止后相机不会继续漂移。
* 瞄准偏移自然。
* 玩家不会因瞄准偏移长期位于屏幕危险边缘。
* 相机边界与关卡边界一致。
* 相机不会显示关卡未完成区域。
* 射击反馈不会影响瞄准。
* 受击反馈不会造成方向迷失。
* 像素或图像采样不会因相机移动持续抖动。
* 当前主要威胁保持可读。
* 当前移动方向前方具有足够视野。

任何一项不通过，相机不得验收。

## 14.7 关卡视觉验收

* 当前关卡具有明确视觉主题。
* 玩家能够立即识别。
* 敌人能够立即识别。
* 子弹和攻击预警能够立即识别。
* 入口、战斗区域和出口能够识别。
* 场景具有明确焦点。
* 背景不会抢夺战斗信息。
* 场景装饰比例统一。
* 场景资产透视统一。
* 光源方向统一。
* 阴影方向统一。
* 玩家与地面接触可信。
* 敌人与地面接触可信。
* 区域过渡自然。
* 不存在明显资源拼贴感。
* 不存在临时占位资产。
* 不存在乱码、问号文本或缺失图标。
* 不存在不必要的视觉空洞。
* 不存在无意义的装饰堆叠。
* 战斗最复杂画面仍然清晰可读。

任何一项不通过，当前关卡视觉不得验收。

## 14.8 UI 验收

* 生命状态清晰。
* 当前武器清晰。
* 武器切换反馈清晰。
* 关键数值清晰。
* UI 不遮挡主要战斗区域。
* 同一句文本的高亮内容使用同一文本节点。
* 字体层级统一。
* 图标尺寸统一。
* 对齐和间距统一。
* 不存在文字截断。
* 不存在文字与图标重叠。
* 不存在不同分辨率下明显错位。
* 不存在占位图标。
* 所有复杂图标均符合统一美术规范。
* 所有简单图标均保持清晰的矢量边缘。
* 战斗中无需长时间观察即可读取状态。

任何一项不通过，UI 不得验收。

## 14.9 完整流程验收

完整流程必须连续测试，不得仅分别验证功能。

至少完成以下测试：

* 连续完整游玩 10 次。
* 每种武器至少完成 3 次完整流程。
* 玩家至少死亡并重开 5 次。
* 战斗过程中多次暂停和恢复。
* 战斗过程中连续快速切换武器。
* 多敌人同时受击。
* 玩家在关卡四周和边界附近战斗。
* 玩家在移动、瞄准、射击、切换武器时受到伤害。
* 清除全部敌人并完成结算。
* 重开后检查所有状态是否恢复。

验收期间不得出现：

* 崩溃。
* 状态卡死。
* 动画卡死。
* 武器失效。
* 敌人不再行动。
* 相机跳变。
* UI 状态残留。
* 死亡后输入残留。
* 重开后资源状态错误。
* 场景切换后音频残留。
* 乱码。
* 丢失资源。
* 明显帧率骤降。
* 明显视觉破坏。

## 十六、完成定义

当前关卡的“完成”不以代码提交数量、场景节点数量或资源数量衡量。

当前关卡只有同时达到以下结果，才视为完成：

* 玩家每一帧移动自然。
* 玩家转向自然。
* 玩家射击自然。
* 玩家武器切换自然。
* 敌人移动自然。
* 敌人攻击可读。
* 敌人每次合法受击均正确结算。
* 敌人受击和死亡反馈清晰。
* 相机移动稳定并服务战斗。
* 关卡空间清晰并服务核心玩法。
* 场景、人物、敌人、特效和 UI 风格统一。
* 当前关卡能够形成完整、稳定、有节奏的战斗闭环。
* 完整流程能够连续通过高强度测试。
* 不存在需要以“暂时如此”解释的明显质量问题。

本阶段的目标不是抢救一个已经失败的项目。

本阶段的目标是建立项目真正的第一块质量基准。

这块基准一旦成立，后续的房间、关卡、敌人、武器和剧情才能稳定扩展；在它成立之前，任何扩展都会继续放大当前的不一致。

因此，当前关卡必须按照正式游戏内容制作，而不是按照原型、演示或临时测试场景制作。
